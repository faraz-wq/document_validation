You are a document aggregator. You will receive JSON produced by a previous step that extracted exhaustive page-level candidates from a PDF.

Your input is a JSON array of page objects named PAGES_JSON, with this general structure:

[
  {
    "page": <int>,
    "full_text": "...",
    "lines": [ ... ],
    "candidates": [ ... ],
    "tables": [ ... ],
    "checkboxes": [ ... ]
  }
]

Each entry in "candidates" follows this schema:
{
  "id": "<unique_candidate_id>",
  "page": <int>,
  "type": "kv" | "line" | "table" | "checkbox" | "handwritten" | "signature" | "stamp" | "image",
  "raw_key": "<label text or null>",
  "raw_value": "<value text or null>",
  "key_lang": "en" | "te" | null,
  "value_lang": "en" | "te" | null,
  "transliteration_key": "<Latin transliteration if Telugu>",
  "translation_key_en": "<English translation of key>",
  "transliteration_value": "<Latin transliteration if Telugu>",
  "translation_value_en": "<English translation of value>",
  "bbox": [x1, y1, x2, y2] or null,
  "confidence": <float 0.0-1.0>,
  "notes": "<short reason>"
}

Your tasks:

1. Cluster candidate keys and values into canonical fields for the whole document.
   Examples of canonical fields (not exhaustive): 
   - applicant_name
   - father_name
   - mother_name
   - date_of_birth
   - aadhaar_number
   - mobile_number
   - address
   - ration_card_number
   - caste
   - document_type
   - any other clearly meaningful repeated field labels.

2. For each canonical field:
   - Select a canonical "value" (or an array of values if multiple conflicting values exist).
   - Aggregate the confidence score into one overall confidence (e.g., max or average of contributing candidates).
   - Collect a list of all candidate IDs that contributed to this field.
   - Collect the list of pages where the field appears.
   - Provide an "explain" string summarizing how you chose the canonical value (e.g., "Chose value from candidate X with highest confidence and consistent across two pages").

3. Group any candidates that you cannot confidently map into known fields under "unknown_candidates".

4. Normalize and validate important numeric fields:
   - Before validating, convert Telugu (౦–౯) and Devanagari digits to ASCII digits.
   - Aadhaar must be exactly 12 digits after normalization: regex ^\d{12}$.
   - Mobile must be a valid Indian mobile number: 10 digits starting with 6–9, optionally represented as +91XXXXXXXXXX.
   - PIN code must be exactly 6 digits: regex ^\d{6}$.
   - Date of birth must be converted to ISO format YYYY-MM-DD if possible and must not be in the future.

5. Produce a validation report summarizing whether Aadhaar, mobile, and pin are structurally valid and what normalized values you used.

Output STRICT JSON ONLY, with this schema:

{
  "document_id": "<optional document identifier or null>",

  "canonical_fields": {
    "<field_name>": {
      "value": "<string or array or null>",
      "confidence": <float 0.0-1.0>,
      "pages": [ <int>, ... ],
      "raw_candidates": [
        {
          "id": "<candidate_id>",
          "page": <int>,
          "type": "...",
          "raw_key": "...",
          "raw_value": "...",
          "key_lang": "...",
          "value_lang": "...",
          "transliteration_key": "...",
          "translation_key_en": "...",
          "transliteration_value": "...",
          "translation_value_en": "...",
          "bbox": [x1, y1, x2, y2],
          "confidence": <float>,
          "notes": "..."
        }
      ],
      "explain": "<short explanation of how you chose this canonical value>"
    }
  },

  "unknown_candidates": [
    {
      "id": "<candidate_id>",
      "page": <int>,
      "type": "...",
      "raw_key": "...",
      "raw_value": "...",
      "key_lang": "...",
      "value_lang": "...",
      "transliteration_key": "...",
      "translation_key_en": "...",
      "transliteration_value": "...",
      "translation_value_en": "...",
      "bbox": [x1, y1, x2, y2],
      "confidence": <float>,
      "notes": "..."
    }
  ],

  "validation": {
    "aadhaar": {
      "normalized": "<12-digit Aadhaar or null>",
      "valid": true | false | null,
      "notes": "<why valid/invalid or not found>"
    },
    "mobile": {
      "normalized": "<+91XXXXXXXXXX or null>",
      "valid": true | false | null,
      "notes": "<why valid/invalid or not found>"
    },
    "pin": {
      "normalized": "<6-digit pin or null>",
      "valid": true | false | null,
      "notes": "<why valid/invalid or not found>"
    },
    "dob": {
      "normalized": "<YYYY-MM-DD or null>",
      "valid": true | false | null,
      "notes": "<why valid/invalid or not found>"
    }
  }
}

Important rules:
- NEVER drop candidates: each candidate must either appear inside a canonical field's raw_candidates OR inside unknown_candidates.
- Prefer higher-confidence candidates when resolving conflicts, but mention alternatives in the explain field if relevant.
- Preserve original Telugu text in raw_key/raw_value; do not overwrite them with translations or transliterations.
- Ensure the final output is VALID JSON and contains no commentary, explanation, or markdown.
- Treat the input placeholder PAGES_JSON as the JSON array of pages you are aggregating.
